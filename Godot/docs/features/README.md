## 章节模板

> 只写**现状**与**计划**。一篇文档要能直接回答两件事：现在是什么样、下一步做什么。

1. **标题 + 一句话概述与状态**
2. **来源与口径** — 需求来源（文档链接 / 设计稿 / 现有实现），注明核对日期与获取方式；
   若无上游文档，须明确写出依据是什么
3. **需求口径** — 需求原文，只节选落到实现的那部分
4. **需求与实现对照表** — 需求 ｜ 状态 ｜ 落点（具体类、常量、文件）
5. **代码与配置** — 目录树 + 每个文件一句话职责；**配表单独一小节**：表名、主键、
   每列含义、哪些是派生值不该配
6. **关键设计** — 易错的机制（坐标系、时序、参数含义），写成**实现约束**，不写成踩坑故事
7. **判据** — 单测用例清单 ／ headless 判据 ／ 回归命令与阈值
8. **拍板记录** — 有分歧的决策与理由（编号供正文引用）
9. **已知问题与待办** — 影响 + 处理方向；未做项的改动点挂在这里

## 维护约定

- **只写现状与计划，不写落地过程**。不写「我改了什么文件」「某日实测」「第一版测试抓到」
  「与本次改动无关」这类流水账，也不要整块「落地实录」：
  - 改动落到哪 → 写进「需求与实现对照表」和「代码与配置」
  - 易错点 → 改写成实现约束（「占比按速率算，不按扣除量算」），不写成「曾经踩过」
  - 判据 → 只留命令与阈值，不记日期流水
- **功能完成即更新**：改动代码后同步更新对应文档，尤其是「需求与实现对照表」的状态位
- 状态位含义：**✅** 已完成 ／ **🔜** 接口就绪、等待上游 ／ **⏳** 未实现
- **所有断言以实际代码为准**：文档与 `CLAUDE.md` / `AGENTS.md` 冲突时以代码为准，并回头订正文档
- 数值类结论尽量附实测依据，便于日后复核，避免后人拿废弃数据当依据白改一版
- 上游文档若在带登录墙的平台上（飞书 / Notion / 内网 wiki），`WebFetch` / `curl` 会 302 到登录页：
  要么用带会话的官方连接器，要么先把关键段落导出成本地副本再引用
